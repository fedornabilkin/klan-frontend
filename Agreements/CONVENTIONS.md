# Соглашения фронтенда

- Используйте Vue 3 Composition API, `script setup` и строгий TypeScript; шаблоны существующих компонентов написаны на Pug.
- Разделяйте отображение, запросы и доменные преобразования. Выносите повторяющиеся сценарии в composables, запросы в services, вычисления в domain. Не создавайте универсальные абстракции для одного случая.
- Для исходников используйте `@/…`, для локальных контрактов — `@shared/…`. Импорт не должен выходить за корень репозитория.
- Сохраняйте русские подписи, единый стиль Naive UI и существующие CSS-токены. Учитывайте клавиатуру, подписи полей, фокус, мобильные размеры и уменьшенное движение.
- Не вставляйте текст профилей как HTML. Ссылки преобразуйте существующим безопасным компонентом; сохраняйте защиту от опасных схем URL.
- Редактирование собственной анкеты выполняйте в соответствующих блоках. Не добавляйте новые модальные формы там, где уже принято редактирование на месте.
- Сервер определяет права и инварианты. Клиентская проверка предназначена для понятной обратной связи и не заменяет серверную.
- Не показывайте скрытые/неподтверждённые результаты как обычные итоги. Пустое значение отличается от явного нуля.
- Добавляйте тесты для значимых преобразований, фильтров, дат и расчётов. Не тестируйте повторно простую разметку только ради покрытия.
- Секреты, реальные данные участников, дампы, отчёты и скриншоты не входят в исходный репозиторий.

## Работа с репозиторием

- Фиксируйте завершённые изменения коммитами. Заголовки и описания коммитов пишите на русском языке; объясняйте смысл изменения. Названия идентификаторов и команд можно сохранять без перевода.
- Команды npm выполняются из `Project/`; приложение, зависимости, настройки Vite и сборка находятся там же.
- Следуйте [архитектуре](../Docs/architecture.md), [требованиям](../Docs/requirements.md) и [инструкции развёртывания](../Docs/deployment.md).
- Не добавляйте файловые зависимости на соседние backend, bot или служебные каталоги. API связывает компоненты во время работы; `Project/src/shared` хранит локальную версию контрактов.
- Сохраняйте текущую модель доступа: интерфейс показывает доступные действия, решение принимает API. Не переносите Telegram-токены, ключи или параметры базы в клиент.
- При изменении поведения выполняйте относящиеся к нему тесты и `npm run build`. Проверяйте затронутые экраны в браузере, если он доступен.
- Файлы Docker хранятся в `Docker/`, серверные конфигурации — в `Deploy/`, локальные сценарии — в `Scripts/`, документация — в `Docs/`, соглашения — здесь. Оставляйте в корне только README, AGENTS и необходимые файлы Git.
- Сборка и запуск не должны читать файлы из соседних репозиториев. Docker build context — корень этого репозитория; Dockerfile-specific ignore находится в `Docker/Dockerfile.dockerignore`.
- Не меняйте реальные данные ради проверки интерфейса. Реальные `.env`, `node_modules`, `dist`, журналы, дампы, выгрузки и результаты ручных проверок не входят в Git. Версионируются только безопасные `.env.example`.

## Синхронизация облачной и локальной работы

- Изменения, подготовленные в облаке, сначала переносите в соответствующий локальный репозиторий пользователя. Сохраняйте историю, незакоммиченные изменения, приватные настройки и данные.
- После проверки локальной копии отправляйте коммиты в GitHub из неё, когда публикация разрешена пользователем и доступна. Не публикуйте напрямую из облачной копии, если пользователь явно не задал другой порядок.
- Если локальная среда недоступна или перенос заблокирован, сохраните подготовленные коммиты для последующего переноса и явно сообщите, что локальная синхронизация и публикация ещё не завершены.
- Изменения проверяйте и коммитьте локально. Отправка в GitHub и выкладка в прод выполняются по отдельной команде пользователя.
